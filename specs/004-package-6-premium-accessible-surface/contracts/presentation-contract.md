# Contract: Package 6 Presentation Truth

## First viewport

The initial desktop viewport names the product story and exposes current implemented revision/outcome, observed outcome, strongest precedent outcome, evidence-only boundary, proposal application state, human authority, and one safe action. It is the working product, not a marketing page.

## Six-stage rail

Exactly six links target real sections. `complete`, `current`, and `available` are derived from committed data; color is never the only state indicator. A link remains inspectable after completion.

## Exact review acknowledgement

Approve/reject/edit/revoke cannot open confirmation until the exact proposal/revision acknowledgement is checked. A proposal digest, base revision, session generation, or variant change clears it. Confirmation and server authority checks remain separate and mandatory.

## Operation panel

Every named state has exactly five public fields: what happened, implemented-revision change (`yes`/`no`/`unknown`), stable code, safe correlation ID, and one safe next action. The action can target a control/section or perform one retry; no panel exposes two recovery actions.

## Receipt and verification

The committed application receipt stays inline after modal close, is copyable, and starts the existing revision-2 rehearsal. Verification names the revision, renders six checks with raw-sequence references, exposes safe projection provenance, and states all four proof exclusions.

## Accessibility

Semantic source order matches visual order. Native dialogs retain accessible name, description, modal semantics, inert background, Cancel-first application receipt focus, and focus return. Targets are at least 44×44 px, focus is visible, motion reduces, live announcements are material-only, and content has no page-level/two-dimensional horizontal overflow at required profiles.
